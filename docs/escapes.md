# Escapes

Defects found after merge, one line each, named by the gate that could have
caught them. The format and the reason the ledger is tracked are in
`skills/writing-retros/escapes-ledger.md`.

| Date | Lane | What escaped | Should have been caught by |
|---|---|---|---|
| 2026-11-03 | session-native (0.4.0) | A background review report was dated when the reviewer stopped, so commits made while it read passed the done gate's freshness check unreviewed. The fix-diff re-review found it after PR 8 merged. | review |
| 2026-11-03 | hook infrastructure | In a desktop-app worktree session every hook ran in the main checkout (the app passes `--project-config-root` there) while the wrappers ran in the worktree, so one session's evidence split across two `.shipshape/` folders and the gates read half of it. Found by the shipdeck session (PR 10), whose doctor reported its captured review missing. | smoke |
| 2026-11-04 | epic coordination (0.3.0) | The epic skills put the epic folder in the shared checkout, but a desktop-app lane runs in a worktree and the app refuses its Write and Edit on the main checkout, so a lane following the skills could not write its own roster file. Found in the field by the post-0.5 epic, which moved to the side-session notes folder. | design |
| 2026-11-04 | per-PR obligations (gates) | `git rev-parse` prints a branch name it cannot resolve and exits 128, so the gates' check for an empty tip never fired on a deleted branch. A stamped PR stayed owing in the done gate, could be denied as stale by the merge gate with the branch's own name as its tip, and read STALE in the doctor. Found during F2's task-fence round, in all three since 2026-08-19. | tests |
| 2026-11-05 | evidence wrappers | `shipshape-pr-open --help` exits 0 and its help carries a URL, so the wrapper armed a record for `cli.github.com/manual`, and shipdeck's band showed a PR that never existed. Found when the live merge test of shipdeck 0.1.4 left `PR` on the band. Its review also found a dry run arming a PR its body links, and a PR gh made before a later failure going unarmed. | tests |
| 2026-11-05 | hooks (pr-wrapper gate) | The gate matched `gh pr create` only as those three words, so `gh pr new` (create's alias in gh's own help), `-R` on either side of `pr`, and `command` or `time` in front each got past it. gh runs every one as `pr create`, so a pull request opened that way would have nothing armed, and the done gate would never ask that branch for its evidence. Found by a review probe, in the gate since 2026-08-09. Create's own flags written before `create`, as in `gh pr --title t create`, still get past; that is open. | tests |
| 2026-11-10 | hooks (pr-wrapper and merge gates) | Both gates piped the command into `grep -q` under `pipefail`. On a long command, such as a 200 KB heredoc body, grep leaving at its match killed the writer and the pipeline read as no match, so the pr-wrapper gate allowed `gh pr create` and the merge gate allowed `gh pr merge` (measured: refused at 60 KB, allowed at 200 KB). Found by the whole-branch review of the spelling fix above, which fixed its own gate; the merge gate's, there since 2026-08-19, was fixed in 0.6.6. | tests |
| 2026-11-10 | hooks (merge gate) | The merge gate matched `gh pr merge` only as those three words, so `gh -R o/r pr merge`, `gh pr -R o/r merge`, `command gh pr merge` and `time gh pr merge` were allowed with no stamp read. Found by the same review; fixed in 0.6.6, where both gates read with one shared pattern. | tests |
| 2026-11-10 | hooks (merge gate) | The merge gate read only a bare number or a `/pull/` URL as the PR being merged and otherwise fell back to the current branch's PR, so a merge that named its PR by branch, in quotes, as `'#58'`, or inside `(…)` or `$(…)` was judged as the current branch's PR, and allowed when that one was stamped. It also read a flag's value as the PR, so `gh pr merge -t 57 58` was judged as 57. gh 2.96.0's usage is `[<number> \| <url> \| <branch>]`. The 0.6.8 reviews found further cases where something ran before or alongside gh and changed which PR it merged while the gate judged the PR of the branch the session was on: a command before the merge (`git checkout feature-58 && gh pr merge --squash`, `cd ../wt2 && gh pr merge --squash`), an unquoted heredoc whose body ran `$(git checkout -q feature-58)` before gh, a merge run in the background beside a checkout, and a pipe from the merge into another command. Found by the whole-branch review of the gate-matching follow-ups; there since 2026-08-19. Fixed in 0.6.8: the gate reads the PR the merge's own words name and refuses any word it can't read; it judges a merge only when nothing runs before it on its line or an earlier one, with only listed names set before gh; it refuses an unquoted heredoc, a backgrounding `&` and a pipe into anything but `tail`, `head`, `cat` or `tee`; and the shared pattern now reaches `{ gh pr merge 58; }`, `X+=1 gh pr merge 58` and `noglob gh pr merge 58`. Fixed in 0.6.9: the shared pattern reaches gh behind a shell keyword (`if gh pr merge 58; then …`, `! gh pr merge 58`) and behind `timeout`, `nice`, `env`, `nohup`, `exec`, `sudo` and `xargs`, each of which used to pass the merge untraced, and the gate refuses each as not first. Still open: a `gh` function or alias defined before the command, which the gate can't see, and commands in front that the pattern doesn't list, such as `stdbuf -o0 gh pr merge 58`. | tests |
| 2026-11-10 | hooks (merge gate) | The merge gate ignored the repository a merge names, so `gh pr merge -R other/repo 64`, `gh -R other/repo pr merge 64` and `gh pr merge https://github.com/other/repo/pull/64` were each judged as this repository's PR 64, and allowed when that one was stamped; so was `cd /other/repo && gh pr merge 64`. Found by the final review of the first rebuild of the row above; there since 2026-08-19. The 0.6.8 review found more prefixes that send gh to another repository and were judged as this one's PR: `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0` setting `remote.origin.gh-resolved`, `GIT_CONFIG_GLOBAL`, `GIT_COMMON_DIR` and `PATH`. Fixed in 0.6.8: a repository named by `-R`/`--repo` or by the URL must match the record's URL; a merge after a `cd` is refused as not first; a `GH_REPO`, `GH_HOST`, `GIT_DIR` or `GIT_WORK_TREE` prefix, with `=` or `+=`, is refused as another repository; and any other name set before gh is refused unless it is one of `GH_TOKEN`, `GITHUB_TOKEN`, `GH_PROMPT_DISABLED`, `GH_DEBUG`, `NO_COLOR`, `CLICOLOR` and `GH_NO_UPDATE_NOTIFIER`; 0.6.9 took `GH_PAGER` and `PAGER` off that list, since each names a program gh can run. Still open: `GH_REPO` or `GH_HOST` set in the environment the command runs in, which the gate doesn't read. | tests |
| 2026-11-10 | hooks (merge gate) | State an earlier Bash call left behind isn't compared with the record. After `git remote set-url origin …`, `gh repo set-default other/repo`, or a `gh` wrapper put first on `PATH`, a plain `gh pr merge 64` on its own line reaches another repository's PR 64 while the gate judges this session's record for 64. The gate reads one command's text, so what an earlier command changed is outside what it sees, like a `gh` function or alias defined earlier and `GH_REPO` set in the environment (both open, above). Found by the third review of 0.6.8; there since 2026-08-19. Open: comparing the record's repository with the checkout's remotes and gh's resolved default would close it. | design |
